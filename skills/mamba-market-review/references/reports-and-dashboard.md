# Snapshots and the Dashboard

## Snapshot files (for day-over-day comparison)

Save one JSON file per run to `reports/{YYYY-MM-DD}/{session-slug}.json`, where `session-slug` is one of `morning-macro` (8am), `evening-futures` (5pm), `midnight`, or `full-study` (2pm). Example path: `reports/2026-09-17/full-study.json`.

Schema:

```json
{
  "date": "2026-09-17",
  "session": "full-study",
  "generated_at": "2026-09-17T20:03:00Z",
  "futures": [
    {"symbol": "ES", "last": 6721.5, "chg_pct": 0.42, "trend_flag": "green"}
  ],
  "tickers": [
    {
      "symbol": "NVDA",
      "lists": ["dow30", "nasdaq100", "megacap_leaders", "semiconductor_ai"],
      "flags": {
        "trend": "green", "relative_strength": "green", "revenue_growth": "green",
        "margin_trend": "neutral", "earnings_growth": "green", "free_cash_flow": "green",
        "debt": "neutral", "valuation": "red", "institutional_ownership": "green", "moat": "green"
      },
      "red_flag_count": 1,
      "notes": "valuation stretched vs 1yr avg P/E",
      "detail": {
        "price": 219.34, "avg50": 213.57, "avg200": 197.95, "year_high": 236.54, "year_low": 164.27,
        "momentum_50d_pct": 2.7, "benchmark_3m_pct": -0.77, "benchmark_used": "QQQ",
        "revenue_growth_pct": 17.9, "revenue_growth_prev_pct": 19.8, "eps_growth_pct": 2.92,
        "gross_margin_pct": 75.0, "gross_margin_4q_ago_pct": 73.4, "op_margin_pct": 66.2, "op_margin_4q_ago_pct": 63.2,
        "fcf_last4q": [21400000000, 48587000000, 34904000000, 22115000000],
        "debt_to_equity": 0.17, "net_debt_to_ebitda": 0.23,
        "pe_ratio": 19.9, "ps_ratio": 49.4, "ev_to_ebitda": 65.7
      }
    }
  ],
  "rollup": {
    "movers": ["..."],
    "multi_red_flag": ["..."],
    "improving": ["..."],
    "watchlist": ["..."]
  }
}
```

Keep every field machine-readable (the flag values, not prose) so Step 5's comparison logic can diff two snapshots directly instead of re-parsing text. `notes` is the one free-text field — use it for anything that doesn't fit a flag.

**`detail` is required, not optional** — it's what feeds the 10-Point Analyzer companion page below. Saving only the categorical flags (green/red/neutral) is not enough; keep the real numbers behind each flag (the ones already pulled from FMP mid-run — this is free, not an extra fetch) so a future session can rebuild the analyzer from the snapshot alone, without re-deriving anything.

To build Step 5's comparison, find the most recent prior file under `reports/*/{same-session-slug}.json` (sort by date, take the last one before today), load both, and diff:
- `tickers[].flags` — any key that changed value
- `tickers[].red_flag_count` — delta
- `rollup.*` — set differences (who's new, who dropped off)
- `futures[].last` — % change from the prior snapshot's `last` for the same symbol

No pruning logic needed yet — plain files under `reports/` are cheap and the history itself is useful (that's also what feeds the dashboard's recent-history strip below). If this grows unwieldy after months of runs, that's a future cleanup, not something to solve now.

## Dashboard artifact

The dashboard is a Claude Artifact (a published HTML page) that gets **updated in place** after every run rather than re-created, so the user has one stable link. Read the `artifact-design` skill (and `dataviz` if the page includes charts/sparklines) before building or rebuilding this page's HTML — don't freehand the styling.

**Finding the existing dashboard:** check for `reports/.dashboard-url.txt` in this skill's directory.
- **If it exists:** read the URL from it, then use the Artifact tool's `read` action on that URL to pull the current published page before republishing (the Artifact tool requires having read a page in-session before you can update it — this applies even though a prior run published it, because a fresh scheduled session has no memory of that). Then `publish` again with that same `url` so it updates in place instead of creating a new artifact.
- **If it doesn't exist (first run ever):** build the page fresh and `publish` it with no `url`. Take the URL the publish call returns and write it to `reports/.dashboard-url.txt`, then make sure that file gets committed so future runs (which may be fresh sessions with no memory of this one) can find it. Tell the user the URL once, the first time — don't repeat it on every subsequent run, since the whole point is that it doesn't change.

**Page content:** the latest briefing (reuse the Step 6 structure, laid out for a screen rather than plain text) plus a compact recent-history strip — e.g. red-flag counts and a couple of headline futures over the last 5-10 sessions of each type, pulled straight from the `reports/` files already on disk rather than recomputing anything. This is meant to answer "how's it trending lately," not to be a full re-derivation of the comparison in Step 5. Add a **Market News & Research** section too — see `references/news-and-research.md` for what goes in it and how to embed it.

**Ticker labeling — every symbol needs its company name.** A bare ticker (`CEG`, `WELL`, `HONA`) isn't self-explanatory even to a regular user — put the company name next to it wherever a ticker appears on the page (flagged-names tables, futures cards, roll-up lists, the study/what's-next prose, quick links), not just in one lookup table. FMP's quote/batch-quote response already includes a `name` field for every symbol pulled during the run — carry it through rather than re-fetching it separately.

**Full universe directory — a full-study (or midnight) session scans more names than the flagged-names table shows.** Don't let "notable movers" and "multi-red-flag" tables be the only place a name appears — a user who wants to check a specific ticker that didn't get flagged has nowhere to look otherwise. Include a complete, searchable directory section (ticker, company name, list membership, price, %chg, red-flag count) covering every name scanned that session, not just the standouts. At 100+ rows this needs client-side search/filter/sort to stay usable, not just free-text search — a dropdown to filter by list membership (Dow 30 / Nasdaq 100 / S&P 500 / sector basket / etc.) and by red-flag count (0, 1+, 2+, ...), plus clickable column headers to sort by ticker, company, price, %chg, or red-flag count. Plain inline JS is fine within the Artifact sandbox (no external script needed) — keep it wrapped in try/catch per the artifact-design guidance on defensive scripting. The 5pm futures-only check and 8am morning macro update don't need this section (nothing to search beyond the already-compact futures tape).

**The Full Universe Directory needs per-name reasoning, not just a red-flag count.** A bare number ("2 red flags") doesn't tell the user which two of the 8 API-backed checklist items are red or why. Give every row two things: (1) a compact "10-Pt Flags" column showing all 8 checklist points as small colored letter badges (green/red/amber/gray for na) so the pattern is visible at a glance across all 200+ rows without clicking anything, and (2) a click-to-expand detail row (a caret/expand button in the ticker cell) that reveals the real numbers behind each of the 8 points (same level of detail as the 10-Point Analyzer — price vs. moving averages, growth percentages, margin now vs. 4 quarters ago, FCF by quarter, D/E, P/E, etc.) plus a one- or two-line auto-generated "why" summary (which items are red, which are green) for that specific name. This needs the same embedded JSON-blob-plus-inline-JS approach as the Analyzer page (a `<script type="application/json">` data island, expand/collapse via plain JS, no runtime capability needed) — reuse the Analyzer's per-point rendering logic rather than re-inventing it, since it's the same 8 numbers either way. Institutional ownership and moat stay qualitative/plan-gated as elsewhere; note that in the expanded detail rather than pretending there's a number for them.

**The Full Universe Directory needs a YTD column, plus EMA 72/210/420 and a chart link per name.** Add a sortable "YTD" column to the main directory table (right after Chg, before Red) — the %change from the last trading day of 2025 to the session's latest close, color-coded green/red like every other %chg cell. TradingView has no public API for pulling indicator values (and its site is unreachable from this sandbox), so EMA 72/210/420 are **not** scraped or approximated — compute them directly from each ticker's own daily closes. Pull `/stable/historical-price-eod/full?symbol={SYM}` once per ticker (this single call also supplies the YTD baseline — find the last record dated before Jan 1 of the current year — so it isn't a second fetch), sort chronologically, and apply the standard recursive EMA formula (`k = 2/(N+1)`, seeded from the earliest available close, iterated forward) for N = 72, 210, and 420. FMP's basic history tier returns roughly 5 years (~1,254 trading days) per symbol, which is enough for all three periods to converge to within a fraction of a percent of their steady-state value — don't bother re-deriving a shorter/cheaper approximation. This is ~277 extra API calls on a full-study session (batch the fetch with modest concurrency, e.g. 5–8 workers, and cache each ticker's raw response locally during the run so a re-run or a later step doesn't refetch); a name with fewer than 72 trading days of history (a fresh 2026 IPO/spinoff) gets `null` for every EMA and YTD rather than a number computed off too little data — render that as "n/a — recently listed" in the UI, never as `0%` or a silently-wrong EMA. Render the three EMAs and YTD as extra `dpoint` entries in the same per-name expand panel the 8-point checklist uses (color green if the latest price is above that EMA, red if below), reusing the existing detail JSON data island rather than a separate blob — just add `ema72`/`ema210`/`ema420`/`ytd_pct`/`exchange`/`listed_2026` fields to each ticker's existing detail object. Separately, give every ticker a small &#8599; chart-link icon next to its symbol in the main row, linking to `https://www.tradingview.com/symbols/{EXCHANGE}-{SYMBOL}/` (exchange from FMP's `exchange` field on `/stable/quote` or `/stable/batch-quote` — don't guess NASDAQ vs NYSE) so the user can pull up any of the 277 charts directly — this is a link for the user's own browser to open, not something this sandbox fetches itself.

**The Full Universe Directory needs a personal Watch column, not just filters.** The user wants to check off names they're personally tracking as they read through the directory — a "Watch" checkbox in its own leftmost column on every row (before the Ticker column), plus a "Watchlist only" filter toggle next to the existing search/list/red-flag controls, with a live count badge showing how many are checked. Because every session regenerates the directory's HTML from scratch, this column and its filter toggle must be rebuilt into the table every run (same markup, same checkbox class/data-sym attributes) — the state itself doesn't need regenerating since it lives server-side (see below), but the column and its wiring do, or a future run will silently drop the feature. Guard the row's existing expand-on-click behavior so clicking the checkbox doesn't also toggle the detail row open (checked state and expand state are independent).

**Watchlist state lives in the artifact's shared `db`, not `localStorage` — Claude can and should read it.** The original build used `localStorage` (per-viewer, private, never readable by Claude) — the user later asked for institutional-ownership/moat research to run specifically on the names they'd checked off, which is impossible if that state never leaves their browser. The dashboard now declares `capabilities: {db: {}}` on publish and stores the whole watchlist as one document, `watchlist/state`, shaped `{tickers: {"AAPL": true, "MSFT": false, ...}}` (a map so unchecking just flips a value to `false` rather than needing a field-delete). Page JS: on load, `await claude.use('db')` (branch on `null` — disable the checkboxes with an explanatory `title` rather than erroring, some views won't grant it), `db.doc('watchlist/state').get()` to hydrate; on each checkbox change, update the in-memory map and `db.doc('watchlist/state').set({tickers: map})` (a full-document replace is simpler and safer here than `update()`, which requires the doc to already exist). To find what's currently on the user's watchlist from a session (for the moat/ownership research below, or anything else), read it with the `ArtifactData` tool: `action: "get"`, `collection: "watchlist"`, `doc_id: "state"`, on the dashboard's URL. This is a real architecture tradeoff the user explicitly chose: the watchlist is no longer purely private-to-browser, it's visible to Claude and stored server-side, in exchange for automated sessions being able to act on it. Don't silently revert to `localStorage` if this ever seems inconvenient — that would quietly break the research-scoping feature below without anyone noticing until they ask why a watchlisted name has no research.

**Institutional ownership and moat get a persistent cache, not a from-scratch WebSearch pass every session — and cover the whole directory, not just flagged/watchlisted names.** Before this, an automated session that spot-checked a name's institutional ownership or moat threw the result away at the end of the session — the next run (even the next day, same ticker still flagged) paid for the same two searches again, with no source link either, and everything outside that session's flagged/watchlisted set just showed `n/a` forever. The user explicitly rejected that scoping: every name in the Full Universe Directory should show this information, not a subset. The cache is what makes that affordable — each ticker only ever needs the expensive full research once; every session after that is a cheap refresh check (or nothing, if it's not due yet). Fix: `reports/moat-ownership-cache.json`, one entry per ticker that has ever appeared in any session's directory:
```json
{
  "ARM": {
    "inst_own_pct": 7.5,
    "inst_own_trend": null,
    "inst_own_summary": "~7.5% institutional; SoftBank's ~86% controlling stake caps available float",
    "inst_own_source": "https://...",
    "moat_verdict": "durable",
    "moat_summary": "Near-monopoly in smartphone CPU IP (~99% share), 22M+ developer ecosystem, high switching costs",
    "moat_source": "https://...",
    "last_deep_check": "2026-09-28",
    "last_quick_check": "2026-09-28"
  }
}
```
Each session's scope is every ticker in that session's directory (all 100-277 of them, whatever the session type scans) — not a flagged-only or Watchlist-only subset:
- **Ticker not yet in the cache:** full research — a WebSearch for institutional ownership and a separate one for moat (see checklist-fmp-mapping.md items 9-10 for query patterns and source expectations), both with a source URL, written into the cache with today's date as both `last_deep_check` and `last_quick_check`. The first session to run under this rule will likely have a large backlog (dozens to 100+ uncached names at once) — that's expected, not a sign something's wrong. Don't silently narrow scope back down to "the important ones" to make the session faster; instead, split the backlog across a few parallel research agents (the `Agent` tool, run in background, batched ~20 tickers each) so it finishes in a reasonable time, then merge their results into the cache before publishing. Every subsequent session only has a handful of genuinely new tickers to fully research (new IPOs, names newly entering the large-cap proxy), so this cost drops sharply after the first backfill.
- **Ticker already in the cache:** don't redo the full research by default. Do one lightweight "anything changed" pass instead — a single WebSearch like `"{TICKER} institutional ownership OR competitive moat news {current month} {year}"` — and update `last_quick_check`'s date regardless of outcome. Only if that turns up something materially different (a real ownership shift, a competitive/moat-relevant headline) redo the full two-search research and bump `last_deep_check`.
- A ticker that leaves this session's universe (e.g. drops out of the large-cap proxy ranking) keeps its cache entry — don't delete it. It'll just stop getting checked until it reappears in some session's directory, at which point its existing entry is still a reasonable starting point (refresh it with a quick check before trusting it if it's been a while).

**Render cached results in the per-name detail panel with the source as a clickable link**, not just prose — the user explicitly asked to be able to review the source themselves. Merge the cache's fields into the same per-ticker `detail` object the rest of the 10-Pt Flags detail row already uses (add `inst_own_pct`/`inst_own_trend`/`inst_own_summary`/`inst_own_source`/`moat_verdict`/`moat_summary`/`moat_source` alongside the existing fields), and update the Institutional Ownership / Moat entries in the detail-row renderer to show the summary text plus a `<a href="{source}" target="_blank" rel="noopener">source &#8599;</a>` link when present, falling back to "Not spot-checked this session — only flagged/watchlisted names get a WebSearch pass" when absent. Don't leave stale boilerplate in the detail panel's closing note claiming these two items are blanket-`n/a` or "a computed proxy" once real spot-checked data exists for some names on the page — that's actively misleading; say instead that they're spot-checked for flagged/watchlisted names only, cached, and refreshed rather than redone from scratch each session.

**The flagged-names table needs the same filter treatment as the directory, not just a static list.** Search box, a list-membership dropdown, and a red-flag-count dropdown (this table is already 4+ only, so its red-flag filter just needs a "4+ / 5 only" style split rather than the directory's full 0-4+ range) — same pattern, same `data-search`/`data-lists`/`data-red` attributes on each row, its own small filter script. Don't skip this just because the table is shorter than the full directory; a user actively narrowing down the flagged names by sector or severity is a real use case (e.g. "just show me the flagged utilities").

**Every dollar price gets a `$` sign — no exceptions.** Stock prices, futures prices denominated in dollars, Bitcoin/crypto prices, market caps — all of them, everywhere they appear on the page (directory rows, flagged-names table, futures cards, Bitcoin section, roll-up prose). A bare number reads as ambiguous even when the context implies currency. The only numbers that should NOT get a `$` are percentages, ratios (P/E, D/E), counts, and non-dollar levels like a Treasury yield or the Dollar Index itself (those are index points, not dollars).

As the last element inside the lead section (after the pull-quote row, before `</section>`), always include this block exactly, even when the session rewrites the lead prose. The 8am and 2pm runs both regenerate the lead, and a run that drops this block breaks navigation. Read each URL from its file (`reports/.analyzer-url.txt`, `reports/.worldwatch-url.txt`); add any new companion page here when it is created. Keep the matching `.page-nav` CSS in the page's `<style>`, and keep both pages in the Quick Links row as well. Inline source links inside the lead paragraphs are still expected on top of this.

**Keep the page chrome; replace only the content.** Both pages carry features the user asked for that live in their CSS/JS rather than in any one session's data: the back-to-top button (`#toTop`, bottom-right, sits above the voice bar), full-width prose (the `max-width: none` override for `.intro`, `.movers-read`, `.spotlight p`, `.study .setup`, `.qcard .hint`, `.detail-why`, `.btc-trend-note`), the page nav above, and on the Analyzer the filter row (List, Sector, Red flags and Sort dropdowns plus "Clear filters", ids `fList`/`fSector`/`fRed`/`fSort`/`fClear`) and its own back-to-top button, and the per-name "Company background" links (the `researchLinks()` JS helper: Yahoo Finance profile, SEC filings 10-K/10-Q or 20-F/40-F for foreign filers, Yahoo financials, Wikipedia), shown in the Analyzer header and in each directory row's expanded detail. In the Sector Spotlight's "Average move and red-flag load by sector" table the heading stays plain text (not a link), but each sector name links to the Analyzer with a `#sector-{Name-With-Hyphens}` anchor (e.g. `#sector-Consumer-Cyclical`); the Analyzer's `applyHash()` reads it on load and opens with that sector filter applied and its first name selected. Keep both sides when rebuilding. **Every ticker symbol on the dashboard links to the Analyzer** via the `<script id="ticker-links">` block at the end of the page (plus its `a.ana-link` CSS): at load it turns every `.tk`, `.chip` and roll-up `<strong>` ticker, and every known ticker mentioned in the prose, into a link to `{analyzer url}#t-{SYMBOL}`; the Analyzer's `applyHash()` opens that name directly. It reads the symbol list from the `directory-detail-data` island, so it covers new names automatically. Keep that script, and keep writing tickers in prose as plain symbols (ideally in parentheses, e.g. "Bloom Energy (BE)") so they get linked; don't hand-write these links. They are built from the ticker in the browser, so they need no data and cover every scanned name automatically. When rebuilding either page, start from the currently published page (you must read it before publishing anyway): keep its `<style>` block and every `<script>` except the data island, and swap in this session's sections, the Analyzer's `analyzer-data` JSON and its intro text. The Analyzer also carries a **scoring legend** (`#legend`, above the list/detail layout: the red-flag count scale plus the per-point flag key, with the per-point scoring rules in a "How each point is scored" dropdown; update those rules there if thresholds ever change) and a **graded red-flag color scale** for the list pills: classes `r0`..`r6` from `'r' + Math.min(count, 6)`, where 0-1 = green (Healthy), 2 = olive (Watch), 3 = amber (Caution), 4 = orange (Flagged), 5 = red (Weak), 6+ = solid deep red (Severe), using the `--sev*` tokens. The detail summary reads "N of 10 checklist points flagged red" (the count covers all 10 points, not 8). Never rewrite the page from a blank template; that is how earlier features were silently dropped.

**Watchlist: two stores, merged by the 8am and 2pm runs.** Each artifact has its own `db`, so the dashboard and the 10-Point Analyzer each keep a `watchlist/state` document shaped `{tickers: {SYM: true|false}, changed: {SYM: ISO-8601 time of the last change}}`. The Analyzer's star button ("Add to watchlist" / "On your watchlist") saves to the Analyzer's own store instantly without leaving the page; its List filter has a "My watchlist" option and watched names show a star. The dashboard checkboxes save to the dashboard's store. The dashboard also still (a) restores names a browser holds in `localStorage` from before Sept 28 and (b) accepts `#watch-SYMBOL` / `#unwatch-SYMBOL` links. Keep all of it, and keep `capabilities: {db: {}}` on both pages (omitting `capabilities` on a republish carries it forward).

**Sync step, every 8am and 2pm run, before rebuilding either page:** read both documents with `ArtifactData` (`action: "get"`, `collection: "watchlist"`, `doc_id: "state"`, once with the dashboard URL and once with the Analyzer URL). For every symbol in either, take the value from the side whose `changed[SYM]` is later; a missing time counts as the oldest possible. If the merged map differs from a side, write it back to that side with `action: "set"`, `if_version` = the version you just read, and `data: {tickers: merged, changed: mergedChanged}`. If a write fails on a version conflict, re-read that side and redo the merge once. Never drop a symbol; unchecked names stay as `false`. The merged watchlist is also what "the user's watchlist" means anywhere else in these docs.

**TRAP Criteria (the user's own checklist) — keep on every publish.**
- **Dashboard `#trap` section** ("TRAP Criteria: What We Look For", placed just before `#news`): the user's slide-1 reference cards for #1 Market Leader, #2 Top Competitor and #3 Institutional Darlings, plus the `#events` "Major Events Calendar" (Earnings Whispers, Forex Factory, Fed FOMC calendar, BLS CPI, BEA PCE, DOL jobless claims, BLS JOLTS, Census housing starts, BLS PPI). The three "Fits today" lists and "Next reports" are computed in the browser by `<script id="trap-screens">` from the `directory-detail-data` island, so they refresh automatically; keep that script and its CSS. Both anchors stay in the page nav ("TRAP Criteria", "Major Events"). Keep the reference text as written; it is the user's material.
- **Analyzer "Best-Candidate Check · TRAP #4 Fundamentals"** box on every name (growing EPS over the last 4 reports with beat/miss and whether expectations are growing, ROIC above 10%, TTM net-margin tier >20 / 11-20 / 7-10 / 6 or less, and caution flags: heavy debt, 2+ missed earnings, eroding moat, ROIC under 5%, capex over 15% of revenue, current ratio under 0.8), plus the "Best candidates (TRAP #4)" sort and the legend row. **Every full-study run must refresh this data:** after building the Analyzer data island, run `python3 skills/mamba-market-review/scripts/trap_fundamentals.py <analyzer_data.json> <trap.json>` (about 3 FMP calls per name) and merge each result into that name's detail as `trap`, and also copy `trap.next_date` into `next_earnings_date` on both the Analyzer and the dashboard `directory-detail-data` islands. Banks and insurers skip the ROIC test (not meaningful), so they are scored out of 2.

**Lead with the market, not the pipeline.** The page's opening section (give it a real title — "The Bottom Line," "Today's Read," or similar, not a vague label) must be genuine market content a reader came for: the macro setup, what's flagged and why, what to watch — written the way a market briefing's lead paragraph would be, not a changelog of what got fixed in this session's data pipeline. Endpoint corrections, screener bugs, data-quality fixes, and scope decisions belong exclusively in the Pipeline Findings section at the bottom, where a reader who wants that detail can find it and everyone else can skip it. If a run involved bug fixes, do not let that fact bleed into the lead section's framing (no "Corrected run" style openers) — the lead section's job is to answer "what do I need to know about the market today," full stop.

**Design system: broadsheet editorial, not a SaaS dashboard.** The user asked for the page to feel like reading a serious financial newspaper rather than an app. Built as an *original* editorial design in that genre — never use any real publication's actual name, logo, masthead typeface, or copy their specific trademarked layout; this stays "Mamba Market Review" with its own invented identity (masthead, tagline, edition-bar) styled in that tradition. Concretely: `Playfair Display` for headlines/mastheads, `PT Serif` for body copy, `Source Sans 3` for UI chrome/labels/data-table text, `IBM Plex Mono` for tabular numerals — all via Google Fonts. Ink-on-newsprint palette (warm cream background, near-black ink, a single oxblood/maroon accent) instead of the boutique-SaaS gold/plum from earlier versions. Flat, rule-based separation (hairline `border-bottom`s, an occasional `3px double` rule for major section breaks) instead of card shadows and rounded corners — `--shadow: none` — reserve rounded pill buttons only for genuinely interactive controls (voice bar, filter selects), since those should still read as UI even inside an editorial page. A drop cap on the lead section's first paragraph, a small-caps "kicker" label above each section headline (e.g. "Markets", "Crypto", "Analysis", "Corrections & Methodology" — categorize by what the section actually is), and a couple of large pull-quote numbers pulled from that session's own facts are the signature editorial touches; keep them serving real content, not decorating for its own sake. Keep the 10-Point Analyzer companion page's palette/type in sync with the dashboard's — same tokens, applied a bit more plainly since it's a lookup tool rather than a briefing.

Keep the page itself simple: it's a personal daily-glance dashboard, not a product. The Artifact sandbox only allows scripts from a small CDN allowlist (cdnjs, jsdelivr, Tailwind's CDN, jQuery) — third-party widget embeds like TradingView's live script (served from `s3.tradingview.com`) are not on that list and will silently fail to load, so don't attempt to embed one. `references/news-and-research.md` covers what to build instead. Beyond that, resist the urge to add live data-fetching or interactivity to the artifact itself (per artifact-capabilities guidance, that would need a declared runtime capability) — regenerating and republishing static HTML after each run is sufficient and much simpler to keep correct.

**Read-aloud and voice command bar.** A fixed bottom bar with buttons to read the full briefing, the Bitcoin section, the flagged names, and the What's Next questions aloud via the browser's built-in `speechSynthesis` (Web Speech API) — no external service, no runtime capability needed, works everywhere.

**Voice quality:** the Web Speech API only exposes whatever voices the visitor's OS/browser ships — there's no way to reach a higher-quality TTS provider (ElevenLabs, etc.) from inside the Artifact sandbox, since that would mean a client-side fetch to a third-party host the CSP doesn't allow (and exposing an API key client-side besides). Do the best that's actually possible instead: default `rate` to ~0.85 and `pitch` to ~0.72 — noticeably slower and lower than any browser's un-tuned default, landing on a deep, laid-back, smooth cadence rather than a brisk announcer read. The user asked at one point for a specific celebrity's voice (a well-known deep, laid-back male voice) — that's not something to build: there's no voice-cloning path available client-side in this sandbox, and even if there were, labeling a synthetic voice with a real person's name misrepresents it as theirs. What they actually wanted was the vibe, which the rate/pitch tuning above delivers as an original, unnamed style rather than an impression of anyone specific — don't attach a real person's name to it.

**Ten voice profiles, not one auto-pick.** The user asked for a curated set of ~10 clear, human, English-speaking voice options spanning different accents/genders (explicitly including African-accented English), with celebrity voices as a reference point for what they meant. Two hard constraints shaped what actually got built, and both are worth restating if this ever needs revisiting: (1) the Web Speech API has no ethnicity field — `lang` (locale, e.g. `en-ZA`, `en-IN`) and a free-text `name` are all it exposes, so **accent/locale is the only honest, available proxy for "English ethnicities,"** not a race/ethnicity attribute that doesn't exist in this API on any platform; (2) actual celebrity voices can't be reproduced here — there's no voice-cloning capability available client-side in the Artifact sandbox, and labeling a synthetic voice with a real person's name would misrepresent it as their voice, which is a hard no regardless of sandbox capability (impersonation). So: **10 fixed profile slots** — American (M/F), British (M/F), Australian (M/F), Indian English (M/F), African English (M — South African/Nigerian/Kenyan locales), Irish (F) — each resolved at runtime to the best real matching voice on the visitor's device via locale + name-based gender heuristics, filtered to English-only (`lang` starts with `en`) and through a blocklist of known novelty/effects voices (Albert, Zarvox, Bells, Whisper, and similar non-human-register macOS joke voices) so every option is actually clear human speech. A profile with no real match on that device shows as "not available on this browser" rather than silently substituting something misleading; a close-but-not-exact match is labeled "Closest match: X" rather than passed off as the real thing. All 10 slots always render so the user sees the full intended menu even on a browser that can only fill half of them. Rate/pitch sliders remain, applying on top of whichever profile is selected. Selection persists to `localStorage` by profile id (re-resolved against `getVoices()` on load, since raw voice objects/names aren't guaranteed stable across sessions) — per-viewer only, not readable by Claude or synced across devices. Also wire an optional voice-command toggle via `SpeechRecognition`/`webkitSpeechRecognition` (feature-detect and disable the mic button with an explanatory `title` if unsupported — this is Chrome/Edge/Safari-only, not Firefox, and can fail silently if the Artifact's embedding context blocks microphone permission; the read-aloud buttons must work regardless of whether voice commands do). Match simple keyword commands (bitcoin/btc, flag, next, brief/dashboard/review, stop) rather than requiring exact phrasing. **The spoken text is hand-written per section to read naturally (numbers spelled out, "%" read as "percent," no markup) — it is not scraped from the DOM.** That means it goes stale exactly like every other section: regenerate all four spoken strings from that session's actual numbers every time the dashboard is rebuilt, the same as the visible text. Keep each section's spoken text short enough to actually listen to (a paragraph or two, not a full read of every row).

**ElevenLabs narration is manual-only — never attempt it from an automated Routine session.** The user has an ElevenLabs connector and asked once whether it could upgrade the read-aloud voice quality; it can (studio-quality TTS vs. whatever the browser ships), and generation itself works fine via `creative_generate_speech`/`creative_get_flow_run_status`. But getting the resulting audio out of ElevenLabs and into the dashboard failed hard: the sandbox's outbound network policy blocks the entire `elevenlabs.io` domain family and ElevenLabs-hosted `storage.googleapis.com` content at the organization level (confirmed via `$HTTPS_PROXY/__agentproxy/status` showing `connect_rejected`/"policy denial" on every host tried — not a transient or per-URL issue). That block applies identically inside every automated Routine session, not just interactive ones, so "generate fresh narration each scheduled run" is not buildable as unattended automation here — it would just burn ElevenLabs credits on every run for audio nobody can retrieve. Given that, the user's explicit call was to **keep it manual**: don't wire ElevenLabs into the automated pipeline at all. Browser `speechSynthesis` (the 10 voice profiles above) stays the sole automatic default for every Routine-generated dashboard. If the user asks for ElevenLabs narration in a live interactive chat session, that's fine to do on request (generate the clips, point them to the ElevenLabs flow URL to retrieve directly since this session can't download the files itself) — just never make it part of the unattended Step 7 publish flow.

**Market Movers & Sentiment gets its own section, not a buried Roll-Up bullet.** The user wants a quick, honest read on overall market sentiment beyond the futures tape — build it from the same session's directory data, not a separate pull. Give it: (1) a breadth stat row (advancing / declining / unchanged counts and percentages, plus the average %chg across the full scanned universe — reuse the `.stats` grid pattern from At a Glance), (2) a short plain-language paragraph naming the *actual* story behind the numbers (which sector or theme is driving the gainers, which is driving the losers, and whether the losers share a common cause — cross-reference the Macro Backdrop/Futures cards so the read is internally consistent, e.g. an oil-heavy losers list should reference that session's WTI move rather than restating it as a coincidence), and (3) two side-by-side tables (reuse the `rollup-grid`/`rcard` pattern) of that session's top 10 gainers and top 10 losers by %chg, pulled directly from the directory's own `data-chg`/`data-price` values so the numbers can't drift from the table above. Place it after Sector Spotlight and before the flagged-names table — it's a sentiment overview that bridges the macro cards above it and the specific worst-offenders list below it. Skip it on sessions that don't scan stocks (5pm futures-only, 8am morning macro) same as the Full Universe Directory itself.

**Bitcoin gets its own section, not just a futures-tape row.** It's the one asset in the universe that trades 24/7, so a single "BTC +X%" card in the futures grid undersells it. Give it a dedicated section with: current price, today's %chg, 52-week range, a plain-language trend read (price vs. 50d/200d averages), and a small grid of 7-day / 30-day / 90-day moves so the user can see momentum at a few timeframes, not just one. Pull the historical closes from `/stable/historical-price-eod/full?symbol=BTCUSD` (same endpoint used for relative strength) and compute the lookback returns directly — no separate endpoint needed. A couple of lines of WebSearch context (ETF flow trends, a notable move) round it out, same sourcing rules as the Market News & Research section. Label the section clearly as reflecting the live price at generation time when the rest of the page is showing a prior close (e.g. a weekend run) — the two timestamps aren't the same and shouldn't be presented as if they were.

## 10-Point Analyzer (companion page)

A second, linked Artifact that lets the user look up any single name from that session's universe and see the full numeric detail behind all 10 checklist points — not just the flag, the actual numbers (price vs. moving averages, revenue/EPS growth %, margin now vs. 4 quarters ago, FCF by quarter, D/E and net-debt/EBITDA, P/E and P/S, and plain-language notes for institutional ownership/moat explaining why those two are usually gaps). The main dashboard's tables only have room to surface the standouts; this page is where "why is this one flagged" actually gets answered for any of the 200+ names scanned, not just the ones that made the roll-up.

**Mechanics mirror the main dashboard exactly, in a second file:** check `reports/.analyzer-url.txt` the same way as `reports/.dashboard-url.txt` — read and update in place if it exists, publish fresh and save the URL if it doesn't. Link the two pages to each other (a back-link on the analyzer, a forward-link in the dashboard's intro and Quick Links). Rebuild it every session that has a full ticker universe (full-study, midnight) using that session's `detail` fields straight from the snapshot being written — the analyzer's data is a straight dump of `tickers[].detail`, no separate computation. Skip it for the evening futures-only check (nothing to look up beyond the futures tape already on the main page).

Implementation-wise this is a single static page: embed the ticker data as a JSON blob in a `<script type="application/json">` tag and render the list/detail interaction with plain inline JS (a searchable ticker list on one side, a detail panel on the other) — no runtime capability needed, since nothing has to be fetched live. A name outside that session's universe isn't in the data and can't be looked up from the page itself; say so on the page and point back to asking Claude directly for a live one-off pull.
